# 机器人通用软件框架

![版本 0.1.0](https://img.shields.io/badge/version-0.1.0-green)

## 写在前面

队内大部分机器人电控代码都使用了一套通用框架，这套框架由板级支持、设备组件、业务模组和任务等部分组成。明确各部分在工程中的位置和职责，有助于复用设备与算法，也便于在更换板卡或新增功能时确定修改范围（也便于在某辆车的电控跑路后他人快速接手代码）。有关软件分层及各层的定义，见[机器人软件系统架构](机器人软件系统架构.md)。

## 工程组织

在多板系统中，各控制板通常具有独立的构建入口。板级工程保存 CubeMX 外设配置及其生成代码，应用软件则按组件、实例、模组和任务组织。

| 部分 | 常见位置 | 主要职责 |
| --- | --- | --- |
| 板级工程 | CubeMX 的 `.ioc` 文件、`Core/`、`Drivers/` | 配置时钟、引脚和中断，初始化片上外设 |
| 公共组件 | `HW-Components/` | 提供板级支持、设备封装、算法和可复用模组 |
| 跨板共享代码 | 顶层 `RobotComponents/` 或 `RobotComponent/` | 定义各控制板共用的通信消息、协议或接口 |
| 实例 | `Instance/` | 设置板端参数，创建对象并绑定对象之间的依赖 |
| 业务模组 | `RobotModules/` 或 `Robot/` | 实现整机及子模组的状态管理、命令生成和输出策略 |
| 任务 | `Task/` 或 `Tasks/` | 组织应用初始化、周期处理和通信调度 |

> 修改跨板通信数据时，应同时核对发送端和接收端的字段含义、单位及超时处理。

## 应用初始化

### 板级入口与任务初始化

在板级工程的 `Core/Src/main.c` 中，`main()` 完成 HAL、时钟和外设初始化后调用应用初始化入口。该入口通常位于 `Task/` 或 `Tasks/` 下的 `main_task.cpp`，常见名称为 `MainTaskInit()` 或 `MainInit()`。同一文件中的 `PrivatePointerInit()` 用于取得任务所需的对象指针。应用初始化还负责准备设备和通信，使任务能够按预定顺序开始执行。

### 对象实例化与指针注册

在 `Instance/` 下，`ins_*.cpp` 文件负责创建对象并设置实例参数。如 `ins_fsm.cpp` 中的 `CreateRobot()` 和 `CreateChassis()` 分别提供整机与底盘实例，`ins_imu.cpp` 中的 `CreateImu()` 提供 IMU 实例。

在 `RobotModules/` 或 `Robot/` 下，使用这些对象的业务类提供指针注册接口。如整机类中的 `registerChassis()` 和 `registerImu()` 分别保存底盘和 IMU 的指针。在 `Instance/` 的组装代码中，可以通过 `registerChassis(CreateChassis())` 将创建的实例绑定到整机。带索引的注册接口应校验索引范围，接收通信管理器的注册接口还可同时绑定发送依赖。

> 必需的对象应在周期任务启动前完成注册。可选对象应具有明确的缺省行为。被多个模组引用的对象应明确其有效期和周期更新的责任归属。

## 周期任务

在 `Task/` 或 `Tasks/` 的 `main_task.cpp` 中，采用定时器调度的实现通常由 `HAL_TIM_PeriodElapsedCallback()` 调用 `MainTask()`，主任务与通信任务的执行顺序也可由调度代码确定。在采用更新与执行分离的实现中，主任务先调用整机对象的 `update()`，随后调用 `run()`。

* 在 `RobotModules/` 或 `Robot/` 的业务类实现中，`update()` 刷新工作时间和输入数据，并可通过 `updatePwrState()` 等内部函数更新状态。
* 在 `HW-Components/` 的设备类实现中，`update()` 用于刷新设备数据。业务模组可读取更新后的测量值，并据此计算控制输出或判断设备状态。
* 在整机与子模组的调用关系中，整机先为子模组生成命令，再按子模组接口约定调用其 `update()` 和 `run()`。

> 应沿任务调用链确认各设备的更新频率，并使控制算法的采样周期与实际调度一致。

## 模组状态机

状态机接口通常定义于 `HW-Components/modules/` 或共享的 `RobotComponents/` 下的 `module_fsm.hpp`，状态枚举也可能单独定义在 `module_state.hpp` 中。常见的工作状态包括失能（`Dead`）、恢复（`Resurrection`）和工作（`Working`），部分实现采用带 `k` 前缀的枚举名。**工作状态**描述模组是否可以执行正常动作，**控制模式**描述工作时使用的命令来源或控制策略，如手动或自动。

状态机头文件声明或实现 `run()`，由其按当前状态分派动作。各状态及公共动作的具体处理通常位于 `RobotModules/` 或 `Robot/` 下的整机类和子模组类中。

| 状态或动作 | 常见处理函数 | 主要职责 |
| --- | --- | --- |
| 失能 | `runOnDead()` | 清理由失能而失效的数据，使模组进入待机行为 |
| 恢复 | `runOnResurrection()` | 等待设备初始化、校准或其他恢复条件满足 |
| 工作 | `runOnWorking()` | 根据有效输入生成本周期命令，并执行或调用子模组执行 |
| 待机动作 | `standby()` | 设置待机输出，可由失能、恢复或其他暂停路径调用 |
| 公共动作 | `runAlways()` | 在状态分支之后执行每周期所需的处理，如更新板间状态 |

在状态机头文件及对应业务类中，`reset()` 用于将内部数据恢复至初始条件。状态转换条件由模组根据应用需求决定，应明确进入工作所需的条件、输入失效时的行为以及重新进入工作前的要求。对于只需在进入状态时执行一次的动作，可根据前后状态的变化触发。

> 调试时应依次检查实例与指针绑定、周期输入与状态更新、状态分支与输出。验证宜覆盖启动、正常工作、输入失效及恢复。

## 写在最后

框架的选型取决于机器人的功能、硬件和开发条件。不同战队会采用不同的组织方式，熟悉所用框架后，队员就能较快定位功能入口、判断改动会影响哪些模组，并在联调时沿数据流查找问题。队内沿用相近的组织方式，也便于队员在不同机器人之间协作和交接。

本文所述的目录和接口来自队内工程中常见的做法，应用时应结合具体需求调整。工程、哨兵、平衡等机器人在设备组合、控制周期和状态转换条件上各有特点，业务模组及其调度方式可能需要较大改动。以周期任务为例，新增一个需要独立运行的控制回路时，应先确定其输入来源、更新频率和输出由谁使用，再决定它在任务中的调用位置。这样可以保留已有设备和算法的使用方式，同时让新功能的依赖关系清晰可查。

接手已有工程时，建议选取一项能单独验证的功能，从板级入口追踪实例组装、任务调度和状态处理，再结合实机现象核对代码行为。维护工程时，宜记录本机的运行入口、关键依赖和状态转换条件，并注明调整过的目录或接口。后续维护者可以据此判断哪些组件可以直接复用、哪些参数和行为需要重新验证。
